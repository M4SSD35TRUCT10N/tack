# tack v0.8.7 – Code-/Dokumentationsreview und Informationsarchitektur

**Planungsstand: DRAFT / NOT STARTED (19.11.2026).**
**Startbedingung:** 0.8.6 ist nach Owner-Freigabe inklusive Windows/Linux/Clang und >=90%-Gates abgeschlossen. Dieses Dokument ist ein Plan, keine vorgezogene 0.8.7-Implementierung.

## Deutsch

### Zielbild
0.8.7 wird kein weiteres Sammelbecken historischer Changelog-Absätze, sondern ein **belegorientierter Code-gegen-Dokumentation-Audit** mit anschließender redaktioneller Neuordnung. Ein neuer Anwender soll nach wenigen Minuten verstehen, was `tack` ist, wie er es baut, konfiguriert und verwendet, und welche Grenzen ausdrücklich existieren.

### Code-gegen-Doku-Matrix (pro Aussage)
- Ausgangspunkt ist der **eingefrorene Quellstand** nach 0.8.6: CLI-Befehle, Parsing, Default-/Fallback-Werte, `tack.ini`, Compiler-/Target-/Profil-Reihenfolge, Sicherheitsverhalten, pfad- und plattformspezifische Einschränkungen, `-j`, Formatter, SBOM/BOM/DOC, Coverage, Reports.
- Für jede verifizierbare Aussage: **Datei + Symbol/Funktion + Referenzbereich + reproduzierbarer Test oder Codebeleg + Dokumentationsfundstelle + Ergebnis**. Kein pauschales `implemented` nur weil der Code kompiliert.
- Abweichungen werden als `DOC_INCORRECT`, `CODE_UNIMPLEMENTED`, `AMBIGUOUS`, `OUTDATED`, `VERIFIED` erfasst, jeweils mit konkret verantwortetem Fix. Sicherheitskritische Widersprüche bleiben blocker.

### Status-Audit von Specs/ADRs
- `draft`: Vorschlag ohne Owner-Entscheidung. `accepted`: Entscheidung ausdrücklich durch Owner bestätigt, aber nicht notwendigerweise umgesetzt. `implemented`: beschriebene Lösung **tatsächlich im Produktcode enthalten und durch geeignete Tests nachgewiesen**. Historisch `superseded`/`deprecated` nur mit dokumentiertem Nachfolger.
- Statuswechsel nur mit Entscheidungsbeleg, Code-/Commitbezug, relevantem Test und gegebenenfalls Owner-Freigabe. `accepted` ist **nicht** automatisch `implemented`.
- Jeder Status besitzt ein Datum, eine nachvollziehbare Begründung und eine referenzierte Umsetzung. Widersprüchliche Status in zwei Sprachen konsolidieren.

### Dokumentations-Informationsarchitektur (erst nach vollständigem Audit umsetzen)
1. **README** bewusst kurz und linear: Nutzenversprechen, 60-Sekunden-Quickstart für Windows/Linux, Bootstrap mit `build/host`, drei Alltagsszenarien (`new`, `build`, `test`), Link zu weiterführender Referenz, aktueller stabiler Release-Status.
2. **Guides** für schrittweise Aufgaben: INI, Targets/Compiler, Coverage-/Ratchets, CI/Parallelisierung, Fehlerdiagnose, `doc`-Export; pro Guide Voraussetzungen, erwartetes Ergebnis, Fehlermodi.
3. **Reference** vollständig, präzise, terminologisch einheitlich (Befehle, Flags, INI-Keys, Ausgabe-/Exitcodes, OS-Abweichungen); nicht doppelt im README und Guides ausformulieren.
4. **ADRs und Specs** für Entscheidungen/Soll-Verträge. **CHANGELOG/RELEASENOTES/ROADMAP** für historische Änderungen und Zukunft; historische RC-Protokolle aus dem Lesefluss der Hauptseiten entfernen, aber nachprüfbar archivieren.
5. **Navigation** über taskorientierte Einstiege, ToC, wechselseitige Links und klare DE/EN-Gliederung. Lange Dokumente strukturiert aufteilen; bestehende externe Links und Anker prüfen/Redirects planen.

### Inhaltliche und technische Qualitätsprüfungen
- Every claim vs frozen source; DE/EN parity; Quickstart tatsächlich unter beiden OS ausgeführt; Link- und Anchor-Check; `tack doc` aus denselben Quellen erzeugen und in Offline-/No-JS-Modus prüfen.
- Syntaxbeispiele `tack --config .\tack.ini` (Windows) und `tack --config ./tack.ini` (POSIX); keine `tack.exe`-Erzeugung im Root; Clang-Freigabematrix korrekt dokumentieren.
- Historische Bemerkungen nicht als aktuelle Statuszusammenfassung ausgeben; pro Hauptseite nur einen sichtbar aktuellen Status mit Datum.
- Verbindlich: test-first bei neu gefundenen Produktfehlern, eigene eng umrissene Aufgaben/ADRs statt beiläufigen Codeänderungen mitten im Textaudit.

### Liefergegenstände / Abnahme
- Verifizierbare Audit-Tabelle Code ↔ Dokument, Defekt-/Entscheidungsjournal, Statusregister für alle ADRs/SPECS, redaktionell verbesserte DE/EN-README und Dokumentnavigation, Link-/CLI-Beispieltestbericht, aktualisierte Versionierungs-/Release-Dokumente.
- Owner liest README **von Anfang bis Ende** wie ein neuer Nutzer; Docs-Build, Linkprüfung, relevante Win/Linux-Quickstarts PASS; keine unbelegte `accepted`/`implemented`-Hochstufung.
- Test- und Coverage-Ratchets aus 0.8.6 **nicht** still verändern; wenn aus Review wirkliche Programmänderungen folgen, separate Freigaben und passende Tests.

Deliver an evidence matrix, ADR/SPEC status register, a readable README and validated links/examples. No preemptive status promotions or test-ratchet changes.
