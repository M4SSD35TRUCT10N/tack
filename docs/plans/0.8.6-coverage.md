# Deutsch

## Ausgangslage und Ziel

Die vom Owner angenommene v0.8.4-Linenabdeckung liegt bei **Windows TDM-GCC/gcov 10.3.0: 3192/5827 = 54,77947 %** und **Linux GCC/gcov 14.2.0: 3228/5708 = 56,55221 %**. Dies sind getrennte HWMs; ein Compiler- oder Plattformwechsel darf nicht als künstlicher Rückschritt behandelt werden.

**Ziel für 0.8.6:** mindestens **90 % ausführbare Produktionscodezeilen** auf **beiden** Plattformen unter stabiler, dokumentierter Messdefinition; keine Absenkung der bestehenden HWMs. Auf der alten Zeilenbasis entspräche das mindestens 5.245/5.827 Zeilen unter Windows und 5.138/5.708 unter Linux. Diese Stückzahlen sind **keine** festen Zukunftsquoten, weil sich der Nenner mit dem Code ändern kann.

## Nicht verwechseln

- **Testinventar-Vollständigkeit:** Jeder `tests/*_test.c` ist erfasst und wird ausgeführt oder durch ein geprüftes plattformspezifisches SKIP begründet. Die bestehende Suite umfasst 25 Testquellen. `24 PASS / 1 SKIP` ist **keine 96-%-Anforderungsabdeckung**.
- **Line-Coverage:** instrumentierte Produktionscodezeilen, die mindestens einmal ausgeführt wurden. Das ist die heute versionierte HWM-Metrik.
- **Branch-Coverage:** eigener Messkanal; zuerst reproduzierbar erfassen und Basis definieren, nicht ohne Ausgangswert 90 % behaupten.
- **Anforderungsabdeckung:** nachvollziehbare Matrix Anforderung/Funktion → positive, negative, Grenz-, Integrations- und Fehlerfalltests. Ziel mindestens 90 % der **identifizierten, prüfbaren** Einträge, mit 100 % für ausgewiesene Sicherheits- und Datenintegritätsregeln; Owner-Review der Matrix erforderlich.

## Vorgehensweise, jeweils ein Arbeitspaket

1. Baseline auf beiden Plattformen erneut reproduzieren und pro Quellbereich nicht ausgeführte Zeilen/Funktionen erfassen. Genau eine Definition von Produktionsquelle/Denominator festhalten.
2. Nach Risiko priorisieren: Pfad-/Traversal-Schutz, Prozessstart/Exitcodes, INI-Grenzen und fehlerhafte Eingaben, Cache-/Relink-Korrektheit, Coverage-Gate/Artefaktintegrität, Compilerwahl/Profile, Reports (TAP/JUnit/JSONL), BOM/SBOM/DOC/FMT.
3. Fehlende Tests als **echte Assertions** ergänzen, nicht bloß Funktionsaufrufe. Negative Pfade, Bounds, Fehlerbehandlung und CLI-E2E gehören dazu.
4. Pro Arbeitspaket GCC/TinyCC Debug/Release und separaten GCC/gcov-Profiler nach Verfügbarkeit prüfen; test source inventory mit Owner-Review aktualisieren.
5. Bei reproduzierbarer Verbesserung neue HWM **nur nach ausdrücklicher Abnahme** und zusammen mit dem Test-Commit anheben. Jede Regression bleibt FAIL; bei fehlendem GCC/gcov nur begründetes Plattform-SKIP.
6. Release erst bei zwei unabhängigen 90-%-Nachweisen, validierter Anforderungsmatrix und reproduzierbaren Windows-/Linux-Gates.

**Nicht-Ziele:** Tests abschwächen; Code oder schwierige Dateien aus dem Nenner entfernen; fremde Toolchain-IDs als vergleichbar ausgeben; Code nur wegen Prozentoptik verändern; Python/CMake/Make/Ninja als neue Projektabhängigkeiten einführen.

# English

## Baseline and targets

Accepted v0.8.4 production line coverage: **Windows TDM-GCC/gcov 10.3.0: 3192/5827 = 54.77947%**; **Linux GCC/gcov 14.2.0: 3228/5708 = 56.55221%**. These are independently accepted platform profiles.

**v0.8.6 target:** at least **90% measured executable production lines on both platforms**, under a stable, audited source set, without lowering either HWM. At the old denominator, this would mean at least 5,245/5,827 lines for Windows and 5,138/5,708 for Linux. Future numerators depend on the **actual** source line count.

Test inventory completeness, executable line coverage, branch coverage, and requirements coverage are **different metrics**. The existing 25-test inventory and `24 PASS / 1 SKIP` result do not prove 96% requirements coverage. Branch coverage needs a measured baseline before a separate numerical commitment. Requirements coverage requires a traceability matrix with positive/negative/boundary/integration/error scenarios. Target at least 90% of defined testable requirements, and 100% of identified critical security/data-integrity rules, subject to owner review.

## One milestone at a time

1. Reproduce Linux and Windows reference profiles and map uncovered production lines/functions.
2. Prioritize input/path safety, process exit codes, parser bounds, cache/relink correctness, coverage integrity, compiler selection, reporting and documentation/SBOM/fmt behavior.
3. Add meaningful assertions and negative CLI end-to-end tests, not superficial lines executed for percentage points.
4. Verify inventory and platform compiler gates after every test change. Run gcov when available; platform-specific SKIP is only legitimate if the required tools are unavailable.
5. Raise the measured HWM only through explicit owner approval within the same accepted revision. Never weaken specs or lower accepted coverage.
6. Release only with separate reproducible >=90% Linux and Windows coverage and a reviewed requirements traceability matrix.

**Non-goals:** artificial exclusions, gaming the denominator, weakened tests, treating unrelated toolchain IDs as comparable, or adding Python/CMake/Make/Ninja as project requirements.
